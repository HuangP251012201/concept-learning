大模型的上下文（Context）

概念学习资料 · 由 concept-learning-material-generator Skill 生成并经人工核查

一、一句话定义

上下文（Context）是大模型在一次生成中能"看到"的全部输入信息，其总长度受"上下文窗口（Context Window）"的 token 上限约束。

二、个人解释

大模型没有"长期记忆"。它每回答一次，都是把"当前能看到的全部文字"重新读一遍来作答——这段"当前能看到的全部文字"就是上下文。

上下文窗口，就是这段文字能装下的最大 token 数。它直接决定了模型"知道什么"：

  • 信息装不下 → 被截断，模型"遗忘"；
  • 装太多无关内容 → 注意力被稀释，成本上升、质量下降。

所以对 Agent 来说，上下文的质量与容量，往往比模型本身更决定表现。

三、核心机制或组成

  • 输入组成：系统提示（System Prompt）+ 对话历史 + 工具返回 + 检索到的资料等。
  • Token 与上下文窗口：文本先被切成 token，窗口是 token 上限；中英文的 token 与字符换算不同。
  • 注意力机制（Attention）：模型在上下文中"选择性关注"相关 token，源自 Transformer（Vaswani et al., 2017）。
  • 上下文工程（Context Engineering）：主动设计"喂给模型什么信息"，如精简、排序、检索增强（RAG）、渐进式披露。
  • 记忆与遗忘：超出窗口的部分被截断，靠外置记忆或摘要来缓解。

四、一个具体应用场景

客服 Agent 处理超长对话：用户断断续续聊了上百轮，早已超过窗口上限。若不处理，模型会"忘记"用户最开始的问题。

这时需要做"上下文工程"：只保留最近 N 轮对话 + 用检索把历史工单中与当前问题相关的片段拉进来，再喂给模型。这样既省 token，又能让模型"记住"关键信息。

五、易混淆点 / 使用边界

  • "上下文" ≠ "上下文窗口"：前者是"内容"，后者是"容量上限"。
  • 上下文 ≠ 长期记忆：超出窗口即"遗忘"，长期记忆需要外置存储。
  • 上下文并非越多越好：无关信息会稀释注意力、增加延迟与成本——所以业界强调"上下文工程"而非盲目塞满。
  • token ≠ 字数：1 个中文汉字通常约 1~2 个 token，英文单词约 1~2 个 token，不能简单按字符估算。
